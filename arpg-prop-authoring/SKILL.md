# ARPG prop authoring

Produce grounded, readable medieval scenery that works from the actual overhead game camera. Preserve meaningful shape and believable construction; spend geometry where it improves the result. Use judgment to complete ordinary reversible art decisions rather than mechanically satisfying a list of named objects.

## Establish the task boundary

Read applicable repository instructions, the approved task and the newest relevant asset manifest/report. Identify current source IDs, reusable ingredients, existing materials and the user's latest specific feedback. Verify implementation facts rather than treating an old review as current. This skill supplies reusable art direction, not a new stage, asset quota or authorization to modify production content.

Respect the current environment's permissions. In a planning/read-only session, inspect and prepare a handoff only. In an authorized source-art task, work on editable sources and review outputs; native imports, Scene replacement, Game launches/builds and production promotion require that scope in the task. A source preview is not evidence of native rendering or performance.

Read only the relevant supporting reference:

- For modelling, foliage, texture work, weathering or architectural module fit: [materials-and-geometry.md](references/materials-and-geometry.md).
- For assemblies, campsite/landscape dressing or placement: [arrangements-and-context.md](references/arrangements-and-context.md).

These references hold the operational guidance. Historical research and individual stage reports retain evidence and decisions; do not duplicate their full contents in prompts or load the entire project history.

## Author and compare

- Distinguish **reusable parts**, **finished props**, **editable arrangements** and **runtime placements**. Reusing planks/rails to build a fence is useful; every plank need not become a separate native Actor, draw or collider. Do not count recolours, rotated copies or mesh components as independent designs.
- Before scaling a technique across a family, finish one representative at believable metre scale and inspect its actual rendered appearance. Use the intended overhead view, a useful oblique/detail view and a scale reference where relevant. For a shared material revision, select a small controlled study before propagating one agreed recipe. Iterate the visible defect before multiplying it.
- Keep comparison lighting, exposure, camera and relative scale consistent. Do not conceal geometry, palette or repetition problems with flattering light, changed exposure or different framing. Use a topology/card view from the same evaluated model when making geometry claims.
- Preserve useful old sources, clean/weathered alternatives and raw licensed intake. Use stable logical IDs plus revision metadata; keep candidates separate from canonical recommendations. Detailed foliage or weave can remain bake sources outside the ordinary gameplay root.
- Reuse licensed images and appropriate existing geometry before inventing everything procedurally. Record source/licence and derivations; technique-reference images do not imply texture-reuse rights. Do not execute downloaded code or upload private project content.

## Validate the work actually changed

Codex owns objective checks; the user judges appearance/readability/feel. Do not ask the user to count triangles, run diagnostics or operate a technical checklist.

Check affected evaluated geometry, normals/UVs, dimensions/pivots, material/image paths and ingredient resolution. Include linked instances and modifiers in per-root triangle totals; distinguish unique source data from evaluated instance geometry. Record enough material/image information to explain the tradeoff. Blender mesh-object counts are not native draw calls, and triangle reduction alone does not establish an FPS improvement.

Inspect the real changed renders. Where Blender portability is promised, copy the final packed file to an isolated location without its external image/library folders, then reopen safely in a fresh background process with script auto-execution disabled. Check dependencies and inspect an actual verification render from that copy. Keep original sources in place. Receipts and valid paths alone do not prove visible quality; staging folders must not become final dependencies.

Reuse genuinely unchanged sheets with provenance; update the actual users of changed shared materials/ingredients. Avoid an all-asset/all-camera rerender or unrelated Game suites for a narrow source-art edit. Native tasks instead need the applicable native integration, lifecycle and cost checks; this skill does not waive repository validation requirements.

Machine Use/Computer Use and native Windows GUI automation are disabled in the user's implementation environment. Use permitted background Blender/image tools and existing native capture/test seams when the task authorizes them. State any remaining objective gap honestly; do not assign it to the user merely because a plugin is absent.

Check only the dependencies needed by the current job, in the process that will run it. Blender's bundled Python may lack Pillow/numpy available in system Python. When environments differ, keep raw rendering in available Blender APIs and use existing system image tools for composition, without adding packages merely to bridge that mismatch.

Use the existing bounded Blender queue/gate for parallel asset work. Current workstation precedent is at most two Blender children, one renderer and four threads per child; follow a task's approved limits. This skill does not request subagents or create a new scheduler. Respect any cleanup rejection; keep ignored staging outside final dependencies rather than bypassing policy.

## Deliver a useful review

Provide ready-to-open labelled images/gallery with stable names/IDs, a concise change list, necessary source/provenance data and clear recommendations/tradeoffs. Separate automated checks, rendered observations, unverified native behaviour and actual human feedback. Preserve limited user likes/rejections accurately; do not mark an entire library approved from a partial review.

Keep optional human feedback to at most three ordinary appearance/readability questions, with no required per-object audit. Stop at the approved task boundary.
